# GameplayRuntime

`GameplayRuntime` is the runtime module in the `NelaricGameplay/Plugins/NelaricGameplay` plugin. It contains the gameplay contracts, reusable project-facing actors, and session transport. The `NelaricGameplay/NelaricGameplay.uproject` project enables the plugin; its `Source/` directory contains the `DemoGame` Runtime module.

The module owns common contracts for rule evaluation, gameplay state, player lifecycle, and activity composition. Match flow, objectives, and scoring belong in optional modules; a persistent world can run without a global match or result. The module builds on Unreal Engine's gameplay and networking systems without requiring a specific genre, backend, ability system, or content-distribution provider. Optional modules may depend on GameplayRuntime; GameplayRuntime must not depend on them.

`UWorldStartupConfig` is a `UPrimaryDataAsset` declared in `Public/World/WorldStartupConfig.h`. It selects a map through the `WorldMap` soft reference and contains both world player policy and defaults for local activities. A startup owner selects and retains the asset before loading its map. `MinPlayersToActivate` is the minimum admitted player count needed to activate world gameplay; `0` removes the gate, while `1` waits for the first player. The world may load and admit players before activation, and falling below the threshold later does not automatically deactivate gameplay. `MaxPlayers` caps admitted players, with `0` adding no framework limit. `bInitiallyAcceptingPlayers` sets the initial admission state, while `bAllowJoinAfterActivation` controls admission after gameplay activates. `HasValidPlayerLimits()` rejects negative values and a positive maximum below the minimum.

In the same startup config, `MinParticipantsToStart` and `MaxParticipants` use `0` for no respective activity limit. `StartPolicy` selects an explicit start or an automatic start when the minimum is met; with a zero minimum, the automatic policy is immediately ready. `JoinInProgressPolicy` rejects or admits participants after an activity starts. `HasValidActivityParticipantLimits()` checks the authored range. `HasValidStartupConfig()` also checks the map reference and enum values, but does not load the map or validate server capacity. These values do not determine whether a running activity ends when participants leave, nor do they override world or server capacity. The asset does not apply its policies or replicate runtime state; authority-side gameplay code must do so on the game thread.

`ANelaricGameModeBase` is the project's default game mode through `DefaultEngine.ini` and selects `ANelaricPlayerController` for connected players. Maps may override the game mode, and derived game modes may choose a more specific controller. The controller sends a departure request to the current server and returns that server's direct approval to its owning client. A destination approval beacon contacts the target server at the caller-supplied address and port before travel. The target game mode's `TransitionBeaconListenPort` defaults to 15000 and can be configured to match that endpoint. The transition subsystem currently supports client-to-client moves: it waits for both replies, starts travel, and verifies the new client connection. The target game mode's `CanAcceptTransition()` currently returns `true`; `TODO(NELARIC-TRANSITION-CAPACITY-INTEGRATION)` marks where the active `WorldStartupConfig.MaxPlayers` must be enforced. Until then, target approval does not enforce capacity, and the beacon does not reserve a place or authorize `PreLogin`.

Gameplay World Settings classes used by this project must derive from `ANelaricWorldSettings`. The project config selects this empty base as the default World Settings class. A gameplay map that needs additional settings should use a subclass. The startup configuration selects its map through a soft reference before the map loads; maps do not select their startup policy through World Settings. Other projects using the plugin may choose their own World Settings class.

The module publicly depends on Unreal's `Core`, `CoreUObject`, `Engine`, `OnlineSubsystemUtils`, `EnhancedInput`, and `GameplayTags` modules. The module owns its internal integration passkey under `Private/Internal/`. Public headers only forward-declare the key where a C++ integration signature needs it; gameplay modules cannot include or construct it through the plugin's public API. The project config selects the classes directly under `/Script/GameplayRuntime`.

The `Nelaric` project prefix is optional for modules, files, globally scoped types, and log categories, provided names do not conflict with existing names. Types inside `Nelaric::` and its nested namespaces must not carry this project prefix; keep the required Unreal type prefixes. `ANelaricCharacter`, `ANelaricPawn`, `ANelaricGameModeBase`, `ANelaricPlayerController`, `ANelaricWorldSettings`, and `UNelaricPawnComponent` retain it because Unreal already defines the corresponding unprefixed types and headers. The module entry files are `GameplayRuntimeModule.h` and `GameplayRuntimeModule.cpp`. The `Nelaric::` C++ namespace and `Nelaric.*` automation suite grouping remain stable.

Native input configuration, tag binding, mapping management, and per-player input preferences are owned by this module. The optional `UPlayerInputComponent` derives from `UPawnInitStateComponent` and coordinates local mappings and binding cleanup across init generations. Concrete action tags and input handlers belong to the consuming game; framework Pawn and Character bases do not bind gameplay controls. Enhanced Input supplies action dispatch and key remapping; Gameplay Tags identify native actions independently of abilities. See [Native input](../../../API/Input/NativeInput.md) for configuration and lifetime rules.
