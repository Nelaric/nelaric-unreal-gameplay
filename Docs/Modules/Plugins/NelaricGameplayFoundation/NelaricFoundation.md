# NelaricFoundation

`NelaricFoundation` is the runtime module in the `NelaricGameplay/Plugins/NelaricGameplayFoundation` plugin. It contains reusable gameplay actors, pawn component initialization, world startup configuration, and session transport. The `NelaricGameplay/NelaricGameplay.uproject` project enables the plugin; its `Source/` directory contains four independent gameplay template modules.

The module builds on Unreal Engine's gameplay and networking systems. Concrete gameplay rules belong to consuming games. `ANelaricPawn` and `ANelaricCharacter` preserve their Unreal base behavior and each create an initialization component. `UNelaricPawnComponent` reads current pawn, controller, and player state context without caching; `UNelaricGameplayComponent` is its Blueprint-spawnable variant.

`UNelaricPawnInitializationConfig` defines local participant classes, stable component IDs, authority/client creation flags, required participants, and Ready dependencies. Participants implement `INelaricInitStateParticipantInterface` or derive from `UNelaricPawnInitStateComponent`. `UNelaricInitStateWorldSubsystem` coordinates Registered, DataAvailable, DataInitialized, and Ready; cyclic dependencies commit Ready as a group before notification. Pawn readiness combines required participant states with a context check and can be revoked. State, generation, and managed dynamic instances remain local. See [Pawn component initialization](../../../API/Pawn/PawnInitialization.md) for configuration, refresh, and cleanup behavior.

`UNelaricWorldStartupConfig` is a `UPrimaryDataAsset` declared in `Public/World/NelaricWorldStartupConfig.h`. `WorldMap` stores a map soft reference. `MinPlayersToActivate` stores the player-count threshold for world gameplay activation, with `0` representing no gate. `MaxPlayers` stores the admitted-player cap, with `0` representing no framework limit. `bInitiallyAcceptingPlayers` and `bAllowJoinAfterActivation` store initial and post-activation admission policy. `HasValidPlayerLimits()` rejects negative values and a positive maximum below the minimum.

The same asset stores activity participant defaults. `MinParticipantsToStart` and `MaxParticipants` each use `0` for no respective threshold or limit. `StartPolicy` stores `Manual` or `WhenMinimumReached`; `JoinInProgressPolicy` stores `Reject` or `Participate`. `HasValidActivityParticipantLimits()` validates the count range. `HasValidStartupConfig()` also checks the map reference and enum values. These functions validate authored data; gameplay code reads and applies the stored policy on the game thread.

`ANelaricGameModeBase` is the project's default game mode through `DefaultEngine.ini` and selects `ANelaricPlayerController` for connected players. Maps may override the game mode, and derived game modes may choose a more specific controller. The controller sends a departure request to the current server and returns that server's direct approval to its owning client. A destination approval beacon contacts the target server at the caller-supplied address and port before travel. The target game mode's `TransitionBeaconListenPort` defaults to 15000 and can be configured to match that endpoint. The transition subsystem accepts client-to-client requests: it waits for both replies, starts travel, and verifies a new client world and an open connection matching the destination host and port within a 30-second deadline. The target game mode's `CanAcceptTransition()` currently returns `true`; `TODO(NELARIC-TRANSITION-CAPACITY-INTEGRATION)` marks where the active `WorldStartupConfig.MaxPlayers` must be enforced. See [network sessions and authority transitions](../../../API/Core/NetWork/NetworkSessionTransitions.md) for request and cancellation behavior.

The project config selects `ANelaricWorldSettings` as the default World Settings class. This Blueprintable class derives from `AWorldSettings`. A gameplay map can use a subclass for additional settings. The map reference belongs to `UNelaricWorldStartupConfig`.

The module publicly depends on Unreal's `Core`, `CoreUObject`, `Engine`, and `OnlineSubsystemUtils` modules. The module owns its internal integration passkey under `Private/Internal/`. Public headers only forward-declare the key where a C++ integration signature needs it; gameplay modules cannot include or construct it through the plugin's public API. The project config selects the moved classes under `/Script/NelaricFoundation` and redirects their former `/Script/NelaricGameplayCore` names so existing asset references can resolve.
